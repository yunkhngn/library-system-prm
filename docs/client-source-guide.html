Hướng dẫn source code Flutter client

Tài liệu này giải thích từng file trong LibIOG6/client: file làm gì, vì sao viết như vậy, dùng thư viện nào. P1, P2, P5 đã xong. Thành viên P3–P4 / P6–P11 dùng lại core/, shared/ và các repository access/ · visitors/ khi thay placeholder.

1. Tổng quan

Client là một codebase Flutter duy nhất chạy cho cả 4 trải nghiệm của hệ thống: app sinh viên (mobile), web thủ thư, web quản trị viên và kiosk. Phần đã code hiện tại là nền móng mà cả nhóm dùng chung, cộng với phần của bạn:

2. Kiến trúc: Feature-first + phân lớp

Kiến trúc là feature-first layered architecture, bản rút gọn của Clean Architecture thường dùng với Riverpod. Code được chia theo hai trục.

Trục 1: chia theo phạm vi (thư mục cấp 1 trong lib/)

app/
Lắp ráp mọi thứ: MaterialApp, theme, router, shell. Là nơi duy nhất "biết" tất cả các feature.
↓ dùng
features/
Từng tính năng nghiệp vụ (auth, librarian, student, admin, kiosk). Mỗi người trong nhóm làm thư mục của mình.
↓ dùng
shared/widgets/
Component giao diện dùng chung, không biết nghiệp vụ.
↓ dùng
core/
Hạ tầng: HTTP, token, lỗi, theme, WebSocket, định dạng ngày giờ.

Quy tắc: lớp dưới không import lớp trên. Nhờ vậy 5 người làm 5 feature khác nhau mà ít khi đụng file của nhau. Ngoại lệ có chủ đích: core/network/api_client.dart gọi features/auth để refresh phiên (xem giải thích ở file đó).

Trục 2: ba lớp bên trong mỗi feature

data/

Gọi API bằng Dio, chuyển JSON ↔ model Dart, đổi lỗi thành ApiException. Không biết màn hình nào gọi nó.

application/

Giữ state và quyết định nghiệp vụ (Riverpod Notifier). Không import widget → dễ test.

presentation/

Màn hình và widget. Chỉ watch state và gọi hành động xuống application/; không gọi Dio trực tiếp.

Vì sao không có lớp domain/? Clean Architecture đầy đủ có thêm domain/ (entity, use case, repository interface). Với đồ án cỡ này, lớp đó chủ yếu sinh thêm file mà không thêm giá trị. Khi một feature có logic phức tạp, có thể thêm sau mà không phải sửa cấu trúc.

5. Các luồng chính

5.1 Khởi động app

main.dart→ SessionController.build() = SessionRestoring→ Router đưa về /splash→ đọc refresh token đã lưu→ có token hợp lệ? → Authenticated : SignedOut→ Router tự chuyển trang

5.2 Đăng nhập

LoginScreen bấm "Đăng nhập"→ SessionController.login()→ AuthApi POST /auth/login→ lưu token, state = Authenticated(user)→ Router redirect

Điểm quan trọng: màn đăng nhập không tự chuyển trang. Nó chỉ đổi state; router thấy state đổi (qua refreshListenable) và tự quyết định đi đâu. Mọi luật điều hướng nằm một chỗ:

Trạng thái phiênKết quả
Đang khôi phụcỞ /splash
Chưa đăng nhập/login, hoặc /session-expired nếu phiên bị hết hạn ngoài ý muốn. Trang public (/login, /kiosk, /dev/...) vẫn vào được.
Đã đăng nhập, mustChangePasswordBị giữ ở /first-password-change, không có lối tắt
Đã đăng nhập, đang ở trang vào (/, /login, …)Về trang chủ theo role: sinh viên /student/home, thủ thư /librarian/overview, admin /admin/overview
Vào khu vực không đúng role/forbidden
URL không tồn tạiMàn "Không tìm thấy trang"

5.3 Token hết hạn giữa chừng

Request bất kỳ → 401→ AuthInterceptor gọi refresh() một lần→ thành công: gửi lại request với token mới | thất bại: expire() → màn "Phiên đã hết hạn"

Access token sống 15 phút, refresh token 7 ngày (theo OpenAPI). Người dùng không phải đăng nhập lại mỗi 15 phút.

5.4 Occupancy realtime (LIB-01 / LIB-02)

GET /occupancy→ OccupancyController nối STOMP /topic/occupancy→ bỏ event có revision cũ hơn→ LIB-01 hero + LIB-02 danh sách people tự refresh

Mất kết nối thì LIB-01 hiện chip đỏ và banner "Dữ liệu có thể đã cũ" kèm giờ cập nhật lần cuối; nút Làm mới gọi lại REST.

5.5 Ghi nhận thủ công (LIB-03)

Chọn sinh viên (lookup mã) hoặc khách→ Vào / Ra→ Lý do (≤ 200 ký tự)→ Xác nhận · một Idempotency-Key→ POST /access/manual

Sinh viên ngoài danh sách đang trong thư viện được tra bằng GET /api/v1/students/lookup?code= (thủ thư/admin; tài khoản nhân viên trả 404 như mã không tồn tại). Nếu mạng rớt sau khi gửi, màn hiện "Chưa xác định được kết quả" và nút Kiểm tra lại gọi GET /access/requests/{key} — không tạo key mới.

lib/app/router.dartthậtP2

Trái tim của điều hướng. Gồm ba phần:

a) routerProvider: tạo GoRouter

final refresh = ValueNotifier<SessionState>(ref.read(sessionControllerProvider));
ref.listen(sessionControllerProvider, (_, next) => refresh.value = next);

return GoRouter(
  initialLocation: Routes.splash,
  refreshListenable: refresh,   // phiên đổi → chạy lại redirect
  redirect: (context, state) => _redirect(ref.read(sessionControllerProvider), state.uri.path),
  ...
);

ValueNotifier là cầu nối: GoRouter chỉ nghe được Listenable, còn trạng thái phiên nằm trong Riverpod.

b) Danh sách route

  • Route ngoài shell: splash, login, first-password-change, session-expired, forbidden, dev/components (chỉ khi kDebugMode).
  • ShellRoute bọc mọi màn thủ thư/admin trong StaffShell (sidebar + thanh trên). Khi chuyển trang chỉ phần nội dung thay đổi, sidebar giữ nguyên.
  • /staff/visitors/:visitorId lấy tham số từ URL cho LIB-05.
  • /staff/manual-access đọc query userId / visitorId / action / code / name để prefills LIB-03 từ danh sách người trong TV hoặc khách ngoài.
  • 8 màn P5 đã nối màn thật. Route admin / sinh viên / kiosk vẫn dùng _placeholder(...).

c) _redirect và _canAccess

Hàm thuần (không phụ thuộc widget) chứa luật ở mục 5.2. Dùng switch trên sealed class SessionState: trình biên dịch bắt buộc xử lý đủ cả 3 trạng thái, quên một trường hợp là báo lỗi ngay.

Vì sao đặt quyền ở router: màn hình không cần tự kiểm tra role; người dùng gõ thẳng URL /admin/accounts cũng bị chặn. (Backend vẫn kiểm tra quyền lần nữa, client chỉ để trải nghiệm tốt hơn.)

10.2 Nhóm khởi tạo (Creational)

1. Singleton

Khởi tạo
Ở: core/network/api_client.dart, core/storage/token_storage.dart, core/realtime/realtime_client.dart

Định nghĩa: đảm bảo một class chỉ có một thể hiện và mọi nơi dùng chung thể hiện đó.

final dioProvider = Provider<Dio>((ref) {
  final dio = Dio(BaseOptions(baseUrl: Env.apiBaseUrl, ...));
  dio.interceptors.add(AuthInterceptor(...));
  return dio;   // Riverpod tạo một lần, lưu lại, mọi ref.read trả về cùng object
});
Vì sao dùng
Interceptor, timeout và base URL phải giống nhau cho mọi request. Kho token phải là một, nếu không chỗ này lưu token mới còn chỗ kia vẫn đọc token cũ. Chỉ nên có một kết nối WebSocket tới server.
Khác Singleton cổ điển
Không dùng static instance hay constructor private. "Một thể hiện" do Riverpod quản lý trong ProviderScope, nên test vẫn thay được bằng bản giả. Singleton cổ điển dùng biến toàn cục rất khó test.
Nếu không dùng
Mỗi màn tự Dio() thì phải gắn interceptor nhiều lần, dễ quên, và refresh token chạy song song gây thu hồi phiên.

2. Factory (factory constructor / named constructor)

Khởi tạo
Ở: user.dart, token_pair.dart, api_error.dart, paged.dart, status_badge.dart

Định nghĩa: đưa logic "tạo object như thế nào" vào một phương thức riêng, người gọi chỉ yêu cầu "cho tôi một object từ dữ liệu này".

// Từ JSON → object, kèm chuyển kiểu (String → enum, num → int)
factory User.fromJson(Map<String, dynamic> json) => User(
      role: UserRole.fromApi(json['role'] as String),
      version: (json['version'] as num).toInt(), ...);

// Một factory trả về nhiều "loại" lỗi khác nhau tùy đầu vào
factory ApiException.fromDio(DioException e) {
  switch (e.type) {
    case DioExceptionType.connectionError: return const ApiException(code: ClientErrorCode.network);
    ...
  }
}

// Named constructor = "công thức" tạo sẵn
const StatusBadge.inside() : label = 'Đang trong thư viện', tone = BadgeTone.success, icon = Icons.login;
Vì sao dùng
Chuyển JSON có nhiều quy tắc (đổi kiểu, giá trị mặc định, lỗi định dạng). Gom vào factory thì cả app chỉ có một nơi biết hình dạng JSON của backend. StatusBadge.inside() đảm bảo mọi màn hiển thị trạng thái giống hệt nhau, đúng từ vựng spec.
Nếu không dùng
Mỗi màn tự viết json['role'] == 'LIBRARIAN'. Backend đổi một trường là phải sửa nhiều nơi.

10.3 Nhóm cấu trúc (Structural)

3. Adapter

Cấu trúc
Ở: core/network/api_error.dart, app/router.dart

Định nghĩa: bọc một giao diện để nó "khớp" với giao diện mà phía kia mong đợi, giống ổ cắm chuyển đổi.

Adapter 1: lỗi Dio / lỗi backend → lỗi của app

// Đầu vào: DioException (thư viện) + JSON ApiError (backend)
// Đầu ra:  ApiException (app) có userMessage tiếng Việt
on DioException catch (e) { throw ApiException.fromDio(e); }

Adapter 2: Riverpod → GoRouter

// GoRouter chỉ hiểu Listenable; trạng thái phiên lại nằm trong Riverpod.
final refresh = ValueNotifier<SessionState>(ref.read(sessionControllerProvider));
ref.listen(sessionControllerProvider, (_, next) => refresh.value = next);
GoRouter(refreshListenable: refresh, ...);
Vì sao dùng
Màn hình không cần biết lỗi đến từ Dio, từ mất mạng hay từ backend; chỉ dùng e.userMessage. Sau này đổi Dio sang thư viện khác thì chỉ sửa adapter.
Nếu không dùng
Màn hình phải catch (DioException) và tự đọc e.response?.data['code'], tức là UI phụ thuộc trực tiếp thư viện HTTP.

4. Facade

Cấu trúc
Ở: features/auth/application/session_controller.dart, core/realtime/realtime_client.dart

Định nghĩa: cung cấp một giao diện đơn giản cho một hệ thống con phức tạp.

// Màn đăng nhập chỉ gọi một dòng:
await ref.read(sessionControllerProvider.notifier).login(identifier: ..., password: ...);

// Phía sau Facade làm 3 việc với 3 hệ thống con:
Future<void> login(...) async {
  final pair = await _repository.login(...);          // 1. gọi API
  await _tokens.save(accessToken: ..., refreshToken: ...); // 2. lưu token an toàn
  state = Authenticated(pair.user);                    // 3. đổi state → router tự chuyển trang
}

RealtimeClient cũng là Facade: bên ngoài chỉ thấy connect(), subscribeJson(), disconnect(); cấu hình STOMP, header xác thực, tự kết nối lại, giải mã JSON đều nằm bên trong.

Vì sao dùng
Màn login, đổi mật khẩu, đăng xuất, interceptor đều cần "đổi phiên". Có Facade thì thứ tự "gọi API → lưu token → đổi state" luôn đúng, không màn nào làm thiếu bước.

Hành vi
Ở: session_controller.dart (SessionState), router.dart (_redirect)

Định nghĩa: hành vi của hệ thống thay đổi theo trạng thái nội bộ, mỗi trạng thái được biểu diễn bằng một class riêng.

sealed class SessionState {}
class SessionRestoring extends SessionState {}
class SignedOut        extends SessionState { final bool expired; }
class Authenticated    extends SessionState { final User user; }

// Mỗi trạng thái → một hành vi điều hướng khác nhau
switch (session) {
  case SessionRestoring():          return Routes.splash;
  case SignedOut(:final expired):   return expired ? Routes.sessionExpired : Routes.login;
  case Authenticated(:final user):  ...
}
login() / refresh() ok SessionRestoring ─────────────────────────▶ Authenticated │ │ ▲ │ không có token logout()│ │ login() ▼ ▼ │ SignedOut ◀──────── expire() ─────────── SignedOut(expired: true)
Vì sao dùng
sealed khiến trình biên dịch bắt buộc xử lý đủ 3 trạng thái; thêm trạng thái mới mà quên xử lý là báo lỗi ngay khi build. Dữ liệu gắn đúng trạng thái: chỉ Authenticated mới có user.
Nếu không dùng
Dùng nhiều cờ rời (isLoading, isLoggedIn, user?) thì có thể xảy ra tổ hợp vô lý như isLoggedIn = true mà user = null, gây crash.
Ghi chú
Đây là biến thể hiện đại của State pattern trong Dart 3 (sealed class + pattern matching). GoF cổ điển đặt hành vi vào từng class con; ở đây hành vi nằm trong switch vì router mới là nơi phản ứng với trạng thái.

8. Chain of Responsibility (Interceptor)

Hành vi
Ở: core/network/auth_interceptor.dart, core/network/api_client.dart

Định nghĩa: yêu cầu được truyền qua một chuỗi bộ xử lý; mỗi bộ có thể xử lý, sửa, chặn lại, hoặc chuyển tiếp cho bộ kế tiếp.

void onRequest(options, handler) {
  options.headers['Authorization'] = 'Bearer $token';
  handler.next(options);              // chuyển tiếp cho mắt xích sau
}

Future<void> onError(err, handler) async {
  if (!shouldRefresh) return handler.next(err);   // không phải việc của mình → chuyển tiếp
  ...
  handler.resolve(await _dio.fetch(options));    // tự xử lý xong → dừng chuỗi, trả kết quả
}
Vì sao dùng
Gắn token, refresh token, (sau này) ghi log hay đo thời gian là các mối quan tâm độc lập. Mỗi cái một interceptor, thêm/bớt không đụng code gọi API.
Nếu không dùng
Mỗi hàm API phải tự gắn header và tự bắt lỗi 401, lặp lại ở hàng chục chỗ.

9. Strategy (dạng hàm)

Hành vi
Ở: paged.dart, auth_interceptor.dart, app_text_field.dart

Định nghĩa: đóng gói một thuật toán thành đối tượng có thể hoán đổi, để class dùng nó không cần biết chi tiết. Dart có hàm là "first-class", nên strategy thường được truyền dưới dạng hàm thay vì interface một phương thức.

// Thuật toán "đọc một phần tử" được truyền vào → Paged dùng cho mọi loại dữ liệu
Paged.fromJson(json, Visitor.fromJson);
Paged.fromJson(json, AccessSession.fromJson);

// Cách refresh và cách xử lý hết phiên được "cắm" vào interceptor
AuthInterceptor(
  refreshSession: () => ref.read(sessionControllerProvider.notifier).refresh(),
  onSessionExpired: () => ref.read(sessionControllerProvider.notifier).expire(),
);

// Quy tắc kiểm tra được truyền vào ô nhập
AppTextField(validator: (v) => PasswordPolicy.validateNew(v, current: ...));
Vì sao dùng
AuthInterceptor nằm ở core/ nhưng không cần import SessionController; nó chỉ biết "có một hàm refresh". Nhờ vậy interceptor độc lập và test được riêng.

10.5 Pattern kiến trúc & ứng dụng

10. Repository

Kiến trúc
Ở: AuthRepository; OccupancyRepository, AccessHistoryRepository, VisitorsRepository, ManualAccessRepository, MyShiftsRepository

Định nghĩa: một lớp trung gian giữa logic nghiệp vụ và nguồn dữ liệu. Phía nghiệp vụ chỉ làm việc với một interface, không biết dữ liệu đến từ REST, cache hay dữ liệu giả.

┌──────────────────────┐ dùng ┌──────────────────────────┐ │ SessionController │ ────────▶ │ «interface» AuthRepository│ │ (application/) │ │ login() refresh() ... │ └──────────────────────┘ └────────────▲─────────────┘ │ implements ┌──────────────────────┴───────────────┐ │ │ ┌──────────┴─────────┐ ┌─────────────┴──────────┐ │ AuthApi (thật) │ │ _FakeAuthRepository │ │ Dio → REST backend │ │ (trong test, trả dữ │ └────────────────────┘ │ liệu dựng sẵn) │ └────────────────────────┘
abstract interface class AuthRepository {
  Future<TokenPair> login({required String identifier, required String password});
  Future<TokenPair> refresh(String refreshToken);
  ...
}

final authRepositoryProvider =
    Provider<AuthRepository>((ref) => AuthApi(ref.read(dioProvider)));

class AuthApi implements AuthRepository { ... }   // gọi REST
Vì sao dùng
Logic phiên (khôi phục, đăng nhập, đổi mật khẩu, hết hạn) là phần quan trọng nhất của P2. Nhờ Repository, session_controller_test.dart kiểm tra được 7 tình huống không cần backend, chạy trong khoảng 1 giây.
Nếu không dùng
Muốn test phải bật backend + database, hoặc không test được. Backend đổi đường dẫn thì phải sửa cả logic nghiệp vụ.
Phạm vi
Mọi feature gọi API trong P2/P5 đều có interface repository + bản API, để widget test override bằng bản giả.

11. Dependency Injection (DI)

Kiến trúc
Ở: mọi Provider; test/widget_test.dart, test/features/auth/session_controller_test.dart

Định nghĩa: một object nhận phụ thuộc từ bên ngoài thay vì tự tạo. Đây là cách hiện thực nguyên lý Dependency Inversion (chữ D trong SOLID).

// Code thật: SessionController không tự new AuthApi
AuthRepository get _repository => ref.read(authRepositoryProvider);
TokenStorage   get _tokens     => ref.read(tokenStorageProvider);

// Test: "tiêm" bản giả vào, code thật không đổi một dòng
ProviderContainer(overrides: [
  authRepositoryProvider.overrideWithValue(_FakeAuthRepository()),
  tokenStorageProvider.overrideWithValue(_MemoryTokenStorage()),
]);
Vì sao dùng
Kết hợp với Repository và Singleton, đây là thứ làm cho code test được. flutter_secure_storage là plugin native, không chạy trong unit test; DI cho phép thay bằng bản lưu trong bộ nhớ.

Dữ liệu chỉ đi một chiều: View không bao giờ tự sửa state. Lỗi dễ lần ra vì chỉ có một nơi đổi state. Logic trong ViewModel không dính widget nên test được bằng unit test thuần.

13. DTO / Immutable Value Object

Ứng dụng
Ở: User, TokenPair, Paged, FieldError, ApiException

Định nghĩa: DTO (Data Transfer Object) là object chỉ mang dữ liệu giữa các tầng. Ở đây chúng còn bất biến: mọi trường là final, constructor const.

Vì sao dùng
State Riverpod phải bất biến để Observer hoạt động đúng: muốn đổi thì tạo object mới (state = Authenticated(newUser)), Riverpod so sánh object cũ/mới để báo UI. Nếu sửa trực tiếp user.fullName = ... thì UI không biết để vẽ lại.

14. Route Guard

Ứng dụng
Ở: app/router.dart (_redirect, _canAccess)

Định nghĩa: một "người gác cổng" chạy trước mỗi lần chuyển trang, quyết định cho đi tiếp hay chuyển hướng.

bool _canAccess(UserRole role, String path) {
  if (path.startsWith('/admin/'))     return role == UserRole.admin;
  if (path.startsWith('/librarian/')) return role == UserRole.librarian;
  if (path.startsWith('/staff/'))     return role.isStaff;
  ...
}
Vì sao dùng
Quyền truy cập nằm một chỗ thay vì mỗi màn tự kiểm tra. Gõ thẳng URL cũng bị chặn. Spec AUTH-02 "không có lối tắt vào app khi chưa đổi mật khẩu" được bảo đảm tại đây.

15. Single-flight token refresh

Ứng dụng
Ở: core/network/auth_interceptor.dart

Định nghĩa: khi nhiều tác vụ cùng cần một kết quả đắt (ở đây là token mới), chỉ một tác vụ thực hiện, các tác vụ khác chờ và dùng lại kết quả.

class AuthInterceptor extends QueuedInterceptor {   // xếp hàng lỗi
  ...
  final alreadyRefreshed = sentToken != _tokens.accessToken;  // đã có người refresh rồi?
  if (!alreadyRefreshed && !await _refreshSession()) { ... }
}
Vì sao dùng
Backend xoay vòng refresh token: dùng một lần là token cũ hết hiệu lực. Dashboard gọi 3 API cùng lúc khi token vừa hết hạn; nếu cả 3 cùng refresh, 2 cái sau dùng token đã bị thu hồi và người dùng bị đá ra.

16. Idempotency Key

Ứng dụngLIB-03
Ở: manual_access_screen.dart, ManualAccessRepository, ApiException.isOutcomeUncertain, core/utils/idempotency.dart

Định nghĩa: gắn một khóa duy nhất cho mỗi thao tác; server thấy cùng khóa thì trả lại kết quả cũ thay vì thực hiện lần nữa.

Vì sao dùng
Thủ thư bấm "Ghi nhận vào", mạng rớt đúng lúc. Gửi lại với key mới có thể ghi trùng; với cùng key thì an toàn. Spec: "không ghi nhận trùng khi thử lại".
Cách cài
LIB-03 mint UUID khi bấm Xác nhận. Lỗi chắc (ALREADY_INSIDE, …) thì xóa key. Lỗi không chắc (TIMEOUT / NETWORK_UNAVAILABLE) giữ key, hiện "Kiểm tra lại" → GET /access/requests/{key}. Đổi mật khẩu cũng dùng isOutcomeUncertain (đăng nhập lại, không thử lại).
